콘텐츠를 코드에서 떼어내기

방치형 RPG 심층을 만들다 0.4에서 신규 콘텐츠를 하나도 넣지 않는 리팩터링을 했다. 강화·스킬·적·존·보스가 코드의 enum과 배열 위치에 묶여 있어서, 콘텐츠를 한 줄 늘릴 때마다 코드를 고쳐야 했기 때문이다.

콘텐츠 enum 직접 참조 228 → 0 UpKind · SkillKind · IconId · BossKind 전부 제거
정적 정의표 1,020 → 712 Balance.cs + Balance.Arena.cs, 줄 수
콘텐츠 행 1개 추가 비용 0줄 기존 행동을 재사용하는 한 코드 변경 없음
빌드 전 자동 검사 15종 실패 차단 10 + 계약 테스트 5
역할 설계·구현·검증 (1인) 엔진 Unity 6000.5 / URP 스냅샷 schema v3 · 0.4.0-core.7 기간 2026.08

왜 고쳤나

구현 속도를 위해 AI 보조로 빠르게 쌓아 올린 코드를 다시 읽다가, 지금은 동작하지만 콘텐츠가 늘고 담당자가 바뀌면 반드시 사고가 나는 지점 네 가지를 발견했다. 기능 버그가 아니라 확장 구조의 문제였다.

  • 콘텐츠 ID와 ordinal 배열이 코드에 병렬로 고정 강화 하나를 추가하려면 enum, 정의 배열, 세이브 배열 길이를 동시에 맞춰야 했다. 하나만 빠뜨리면 조용히 어긋난다.
  • enum이 “종류”와 “실행”을 동시에 대표 switch 한 덩어리가 콘텐츠 목록이자 행동 구현이라, 새 콘텐츠와 새 행동의 경계가 없었다.
  • 서로 종속된 규칙이 여러 파일에 흩어짐 스킬 슬롯 수 4, 마지막 슬롯 3, 빈 슬롯 -1이 저장·로직·UI·렌더러에 각각 적혀 있었다.
  • 전역 접근이 테스트와 교체를 막음 Game.I와 정적 저장소 때문에 저장·시계·콘텐츠를 갈아끼울 수 없었고, 그래서 자동 검증도 붙지 않았다.

이 판단은 AI 산출물을 그대로 수용한 결과가 아니다. 구현과 반복 수정은 AI가 맡아 속도를 냈고, 제품 수명·확장성·호환성·인계 위험은 사람이 판단해 방향을 되돌렸다.

세 갈래로 나눴다

“전부 데이터로 뺀다”가 아니라, 값의 성격에 따라 소유자를 정했다. 무엇이 데이터고 무엇이 코드인지가 흐릿한 게 원인이었기 때문이다.

콘텐츠 = 데이터 행

강화·스킬·노드·적·접두사·존·보스·미션. 안정 문자열 ID를 정본으로 쓰고 수치는 전부 스냅샷에 둔다.

실행 = 등록된 계약

행동·효과·표현은 behaviorId / effectId / visualId로 조회한다. 등록되지 않은 ID는 로드 자체가 거부된다.

구조 = 명명된 시스템 규칙

슬롯 수·트리 배치·풀 크기처럼 여러 계층이 공유하는 값만 GameSystemRules에 모았다. 밸런스 수치까지 상수화하지는 않았다.

구버전 세이브 호환을 위한 ordinal은 없애지 않고 legacy_map.json과 변환 코드 네 곳에만 격리했다. 그 네 곳은 [Obsolete]로 표시해, 새 코드가 실수로 ordinal에 손대면 컴파일 경고가 뜨게 했다.

제작은 스프레드시트에서

콘텐츠가 데이터가 되자 편집기가 필요해졌다. Google Sheets를 원본으로 쓰고, Unity 메뉴 하나가 내려받기·검증·생성을 처리한다. 인증 키나 SDK는 쓰지 않고 공개 시트의 공식 CSV export만 읽는다.

01Google Sheets11개 탭. 기획이 여기서만 편집한다
02CSV 내려받기staging 폴더로 격리
03전체 검증하나라도 실패하면 기존 데이터 유지
04JSON 스냅샷manifest + 11개 도메인, 원자적 교체
05런타임검증된 JSON만 읽는다. 네트워크 없음
실제 콘텐츠 시트 열기 이 게임이 지금 쓰는 원본 데이터. 읽기 전용으로 공개돼 있다 Google Sheets ↗

시트에서 값을 고치고 Ctrl+Shift+G 한 번이면 CSV와 런타임 JSON이 함께 갱신된다. 실측으로 11개 탭 중 10개가 로컬 원본과 바이트 단위로 일치했고, 나머지 한 개는 55.00이 55로 정규화된 차이뿐이었다.

깨질 수 있는 건 빌드 전에 막는다

데이터를 사람이 편집하게 만들면 잘못된 데이터가 반드시 들어온다. 그래서 모든 Player 빌드 앞에 validator를 세웠다. 아래는 실제로 로드를 거부시키는 조건들이고, 각각 “일부러 망가뜨린 스냅샷이 거부되는가”를 테스트가 확인한다.

  • 지원하지 않는 schema
  • 도메인 체크섬 불일치
  • 중복 ID
  • 누락된 현지화 키
  • 미등록 behavior ID
  • 미등록 visual ID
  • 존 → 삭제된 적 참조
  • 노드 → 없는 분기 참조
  • 도메인 간 버전 혼합
  • manifest 의존성 누락

manifest.json은 파일 목록이 아니라 계약이다. 11개 도메인 각각의 콘텐츠 버전, SHA-256, 그리고 의존성(zones → enemies)을 들고 있어서, 일부만 잘못 내려받아 서로 다른 세대의 데이터가 섞이는 상황을 로드 전에 잡아낸다.

  • v6 → v7 세이브 변환
  • 구버전 롤백 미러
  • 미래 ID 보존
  • 결정론적 층 구성
  • 주입된 저장소·시계·카탈로그

이 테스트가 실제로 결함 하나를 잡았다. 구버전 슬롯 배열이 없는 새 세이브에서 기본 스킬을 채운 직후 롤백 보정이 다시 비우는 경로였다. 사람이 플레이로 발견하기 전에 검증에서 먼저 걸렸다.

총 코드량은 오히려 늘었다. 늘어난 쪽이 검증·호환·도구이기 때문에 “LOC가 줄었다”로 말하지 않고, 바뀌기 쉬워졌는가로 나눠서 본다.

빌드 경고 4건은 남겨둔 것이다. 전부 NodeDef.Id(v0.3 ordinal)를 쓰는 호환 코드에서 나오며, “ordinal을 만지는 곳은 이 네 곳뿐”이라는 사실을 컴파일러가 계속 세어주는 역할을 한다.

아직 아닌 것

콘텐츠는 데이터가 됐지만 배포 단위는 여전히 빌드다. 스냅샷은 Resources로 패킹돼 실행 파일 안에 구워지므로, 시트를 고쳐도 재빌드해야 반영된다. 빌드를 열어보면 실제로 "contentVersion": "0.4.0-core.6"이 그대로 박혀 있다.

원격 콘텐츠 다운로드·캐시·서명은 구현하지 않았다. 다만 스냅샷이 이미 버전과 체크섬을 가진 아티팩트이고 읽어오는 경로가 추상화돼 있어서, 서버가 필요해질 때 같은 스냅샷을 클라이언트와 서버가 함께 소비하는 형태로 확장할 수 있다. 지금 이 게임에 서버를 도입할 이유는 아직 없다고 판단해 넣지 않았다.
